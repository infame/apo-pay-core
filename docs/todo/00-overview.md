# 00 — Обзор: Автономный платёжный оркестратор

> Зонтичный документ созвездия репозиториев. Держит общую архитектуру, стек, хостинг, модель безопасности и конвенции. Все отдельные ТЗ (`01`…`05`) ссылаются сюда и не должны ему противоречить.

---

## 1. Что это и зачем

**Идея:** система, в которой LLM-агент принимает намерение («заплати по инвойсу», «сделай рефанд по спорной транзакции», «выбери роут платежа»), рассуждает и вызывает инструменты, а детерминированный слой гарантирует, что деньги не задвоятся и не потеряются при сбоях.

**Ключевой инженерный тезис (он же нарратив для собеседований):** стык детерминированной надёжности денег и недетерминированности LLM. Агент не двигает деньги напрямую — он **предлагает** действия, которые проходят через детерминированный policy-слой и исполняются надёжным ядром. Ошибка в таком домене стоит денег, поэтому агентность сознательно ограничена и измеряется (evals).

**Целевой сигнал:** senior → staff backend. Упор на бэкенд (>80% работы). Фронт — минимальный, только чтобы было что потыкать.

**Что это НЕ:** не настоящий платёжный провайдер, не production-платёжка. Эквайер — симуляция. Цель — продемонстрировать инженерное мышление, а не пройти PCI-аудит.

## 2. Созвездие репозиториев

| # | Репо | Роль | AI внутри? |
|---|------|------|-----------|
| 01 | `pay-core` | Детерминированное платёжное ядро: транзакции, идемпотентность, state machine, симуляция эквайера | Нет |
| 02 | `durable-ledger` | Durable execution, double-entry ledger, саги/компенсации, exactly-once | Нет |
| 03 | `agent-orchestrator` | Agent graph: намерение → план → вызов инструментов ядра через policy-слой (guardrails) | Да |
| 04 | `agent-evals` | Eval-харнесс: adversarial-сценарии, метрики надёжности агента | Да (как объект тестирования) |
| 05 | `orchestra` | Головной: монорепо-оркестрация, docker-compose, демо-сценарий end-to-end, диаграммы, live-ссылки | — |

**Зависимости (направление вызовов):**

```
agent-orchestrator ──▶ pay-core ──▶ durable-ledger
        │                 ▲
        └──▶ policy ───────┘
agent-evals ──▶ agent-orchestrator (+ pay-core для проверки эффектов)
orchestra ──▶ поднимает и связывает всё
```

Контракт `pay-core` — базовый. Всё остальное строится на нём, поэтому он проектируется и стабилизируется первым.

## 3. Общий стек

Единая экосистема — осознанный сигнал, что кандидат держит сложность в одном языке.

| Слой | Выбор | Обоснование (кратко) |
|------|-------|----------------------|
| Язык | TypeScript (strict) | единый язык на весь стек |
| Рантайм | Node.js 22 LTS, ESM | современный дефолт |
| Пакетный менеджер | pnpm + workspaces | быстрый, строгий, монорепо из коробки |
| Монорепо-таскраннер | Turborepo | стандарт TS-монорепо, кэш тасков |
| HTTP | Hono | лёгкий, типобезопасный, не Express |
| Валидация границ | Zod | единый источник типов для входа/выхода |
| БД | PostgreSQL | транзакции, блокировки — критично для денег |
| Доступ к БД | Drizzle ORM | близко к SQL, типобезопасно, контроль над транзакциями |
| Durable execution | Inngest | durable без тяжёлого сервера (см. §6) |
| LLM | Anthropic SDK (`@anthropic-ai/sdk`) | tool-use; за адаптером для mock/live |
| Agent graph | свой минимальный движок | ценность в понимании механики, не во фреймворке |
| Тесты | Vitest + Testcontainers (Postgres) | честные интеграционные тесты, без моков БД |
| Контейнеризация | Docker + docker-compose | одна команда поднимает всё |
| Хостинг | Fly.io (осн.) / Railway (запасной) | scale-to-zero, оплата по факту (см. §7) |
| Фронт демо | HTMX + серверный HTML | ноль React-возни, backend-only |
| Диаграммы | Mermaid в README | архитектура + sequence прямо в репо |

**Сознательно отклонённые варианты** (каждый фиксируется в README соответствующего репо разделом «рассмотрено и почему нет»): Express (устаревает как сигнал), NestJS (тяжёлый, декораторный — прячет механику), Prisma (меньше контроля над SQL для денег), XState (FSM пишется руками ради прозрачности), LangGraph.js (прячет механику агента — наш главный дифференциатор), Temporal (overkill для «одна ссылка потыкать» — см. §6).

## 4. Конвенции (общие для всех репо)

**Структура репо:**
```
<repo>/
  src/
  test/
  README.md          # что это, как запустить, «рассмотрено и отклонено»
  package.json
  tsconfig.json      # extends из корневого пресета
  Dockerfile
```

**TypeScript:** `strict: true`, `noUncheckedIndexedAccess: true`, ESM (`"type": "module"`), `moduleResolution: "bundler"` или `"nodenext"` (зафиксируем в корневом пресете). Явные типы на экспортах.

**Стиль кода:** современный TS как отдельный сигнал — `satisfies` для конфигов, discriminated unions для состояний, exhaustive switch с `never`-проверкой, `using`/`Symbol.dispose` для ресурсов (коннекты, локи), Zod на всех внешних границах.

**Именование:** kebab-case для файлов, camelCase для переменных, PascalCase для типов. Таблицы БД — snake_case.

**Ошибки:** доменные ошибки — типизированные (discriminated union или классы-наследники), не голые строки. Границы HTTP переводят доменные ошибки в коды.

**Тесты:** каждый репо зелёный на `pnpm test`. Интеграционные тесты поднимают реальный Postgres через Testcontainers.

**CI:** GitHub Actions на каждый пуш — линт, типчек, тесты. Зелёные бейджи в README. `agent-evals` дополнительно публикует отчёт (дозированно).

**Документация:** README головного репо — точка входа. В каждом репо короткий README + раздел архитектурных решений.

## 5. Модель безопасности live-ссылок

Проблема: публичная демка не должна жечь LLM-баланс и не должна палить ключ, но техком/рекрутер по желанию должен мочь потыкать «по-настоящему».

**Два режима LLM:**
- `mock` — детерминированный фейк-LLM. **Дефолт для публичной демки.** Ноль стоимости инференса, воспроизводимо, работает без ключей.
- `live` — реальный Anthropic-ключ. Включается **только** по валидному подписанному гранту.

**Механика гранта (без админки):**
1. Скрытый endpoint `POST /internal/grant`, защищён секретным заголовком (`X-Admin-Secret`, лежит в env, знаю только я). Может присутствовать в доке как «gated», но бесполезен без секрета.
2. В ответ — подписанная ссылка (HMAC/JWT) с ограничениями: TTL (напр. 24ч), лимит live-запросов на грант, опц. привязка к первой открывшей сессии.
3. Открытие ссылки → сервер валидирует подпись и срок → выдаёт короткоживущую сессионную куку → `live`-режим доступен, пока сессия жива.
4. **Ключ никогда не покидает сервер.** Фронт дёргает наш backend, backend сам ходит в Anthropic.
5. Жёсткий rate-limit на live как страховка бюджета: максимум потерь при утечке ссылки = этот лимит.

Реализация живёт в `orchestra` (§05). Сигнал на собесе: разделение публичного безопасного режима и gated-режима с эфемерными подписанными грантами.

## 6. Почему Inngest, а не Temporal

Оба решают: выполнить многошаговый процесс так, чтобы он пережил падение, не потерялся и не задвоился.

**Temporal** — отдельный сервер/кластер + воркеры + своя БД (часто ещё поиск). Промышленный стандарт, максимальный вес. Минусы под нашу задачу: несколько тяжёлых контейнеров, заметная кривая обучения, живая демка на бесплатном тире практически нереальна.

**Inngest** — библиотека + лёгкий dev-server. Пишешь обычные функции, разбитые на `step.run(...)`; каждый шаг durable и exactly-once. Плюсы: простая ментальная модель, быстрый `docker compose up`, наглядный локальный dashboard (видно шаги, ретраи, падения), реалистичная бесплатная демка.

**Решение: Inngest.** Durable-паттерны (steps, компенсации, идемпотентность) будут в любом случае — на собеседовании мы говорим на языке концепций, а не конкретной либы. README `durable-ledger` содержит честный разбор трейд-оффа. Это и есть staff-сигнал: осознанный выбор под контекст, а не самый тяжёлый инструмент ради веса.

## 7. Хостинг и стоимость

Нагрузка ожидается околонулевая (единицы заходов в день, короткие сессии, `mock` по умолчанию). Разница между провайдерами — не в трафике, а в том, берут ли деньги за сам факт «висения».

- **Fly.io (основной):** оплата за реально работающие ресурсы, scale-to-zero (машины спят при простое). Под наш кейс счёт близок к нулю. Риск-точка — managed Postgres может тикать постоянно; берём минимальный инстанс, проверяем. Чуть больше первоначальной настройки (`fly.toml`) — но это полезный переиспользуемый навык.
- **Railway (запасной):** проще всего задеплоить из GitHub, обычно есть ежемесячный кредит; при нашем трафике укладываемся в кредит или платим единицы долларов. Сервисы засыпают менее агрессивно.
- **Render:** free-тир со сном, но бесплатный Postgres исторически протухает — раздражающий риск для долгоживущей демки. Третий приоритет.

**Важно:** деплой-таргет абстрагирован (docker-compose + env). Не прибиваемся к вендору — можно переехать Fly↔Railway без переписывания. Точные актуальные цены/лимиты проверяются непосредственно перед деплоем, не по памяти.

## 8. Сквозной демо-сценарий (единый для всего созвездия)

Один нажатием-запускаемый сценарий, показывающий весь стек:

> **«Оплата по инвойсу с двусмысленной суммой»**
> 1. Приходит намерение: «оплати инвойс вендору», сумма в описании неоднозначна.
> 2. `agent-orchestrator` рассуждает, распознаёт неоднозначность, уточняет / выбирает безопасную интерпретацию.
> 3. Предложенное действие проходит **policy-слой** (лимит, approval-гейт).
> 4. `pay-core` создаёт транзакцию (идемпотентно), дёргает симулированного эквайера.
> 5. **Эквайер падает** на первой попытке → `durable-ledger` ретраит (durable step).
> 6. Успех → двойная запись в ledger.
> 7. Сценарий отмены → компенсация откатывает, ledger остаётся сбалансированным.

Наблюдаемость: в Inngest dashboard видно каждый durable-шаг; в демо-UI видно шаги агента и статусы транзакций. `agent-evals` прогоняет вариации этого сценария как adversarial-тесты (задвоение, prompt injection в описании инвойса).

## 9. Порядок сборки

1. `pay-core` — фундамент (state machine, инварианты, схема БД, API).
2. `durable-ledger` — надёжность поверх ядра.
3. `agent-orchestrator` — агент + policy.
4. `agent-evals` — доказательство безопасности агента.
5. `orchestra` — связывание, демо, live-ссылки, деплой.

Правило под «разбираться в каждой строчке»: не переходить к следующему репо, пока текущий не запускается, не покрыт тестами и не может быть объяснён вслух построчно. ТЗ на каждый следующий репо пишется после стабилизации предыдущего, чтобы контракты были реальными, а не угаданными.
