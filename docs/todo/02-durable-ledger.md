# 02 — ТЗ: `durable-ledger` (надёжность, ledger, компенсации)

> **Версия 2.** Синхронизировано с `01-pay-core` v2 (имена — как в коде): агрегат `Payment`, эндпоинты `/payments/*` (отмена — `cancel`, не `void`), ошибки `ProviderDeclinedError` (402) / `ProviderUnavailableError` (503). Ссылается на `00-overview`. Никакого AI внутри.
>
> **Ценность репо:** staff-level понимание consistency, exactly-once, саг и двойной записи.

---

## 1. Область ответственности

**Что делает:**
- Durable execution многошаговых платёжных воркфлоу (Inngest): процесс переживает падение и продолжается с несделанного шага.
- Exactly-once эффекты: ретраи не создают дублей (опираясь на идемпотентность `pay-core`).
- Саги с компенсациями: провал на шаге N → откат шагов N-1…1 в обратном порядке.
- Double-entry ledger: append-only журнал проводок + баланс как проекция.
- Наблюдаемость: каждый durable-шаг виден в Inngest dashboard (часть демо-эффекта).

**Что НЕ делает:**
- Не владеет state machine платежа — это `pay-core` (§01). Здесь только оркестрация вызовов к нему.
- Не ходит к эквайеру напрямую — только через HTTP API `pay-core`.
- Нет LLM.
- Не принимает решений «что делать» — решения приходят от `agent-orchestrator` (§03), уже провалидированные policy-слоем.

**Разделение ответственности (для README):** `pay-core` даёт **безопасные для повтора** операции. `durable-ledger` пользуется этим, чтобы строить надёжные распределённые процессы. Это намеренная граница.

## 2. Контракт с `pay-core` (v2 — сверено)

**Эндпоинты, которые дёргаем:**

| Операция | Вызов |
|---|---|
| authorize | `POST /payments` + `Idempotency-Key` |
| capture | `POST /payments/:id/capture` + `Idempotency-Key` |
| refund | `POST /payments/:id/refund` + `Idempotency-Key` |
| cancel | `POST /payments/:id/cancel` + `Idempotency-Key` |
| чтение | `GET /payments/:id` |

**Классификация ошибок — критичный контракт:**

| Код от `pay-core` | Ошибка | Ретраить? |
|---|---|---|
| `503` | `ProviderUnavailableError` | **да** — транзиентный сбой |
| `402` | `ProviderDeclinedError` | **нет** — терминальный отказ → компенсация |
| `422` | `IllegalStateTransitionError` / `AmountExceededError` | **нет** — баг или гонка, логируем громко |
| `409` | `IdempotencyConflictError` | **нет** — неверная генерация ключей, громкая ошибка |
| `404` | `PaymentNotFoundError` | **нет** |
| таймаут / сеть / 5xx | — | **да** |

Реализуется функцией `isRetryable(error)` — явной, покрытой тестами. **Не «ретраим всё подряд»** — это типичная ошибка, и её отсутствие видно из кода.

**Генерация `Idempotency-Key`:** детерминированно от `runId` воркфлоу + имени шага, например `hash(runId + ":" + stepName)`. Так повтор шага Inngest'ом даёт **тот же ключ** → `pay-core` вернёт снимок вместо второго эффекта.

## 3. Двойная запись (ledger)

### 3.1. Почему double-entry, а не колонка с балансом

Однострочный баланс (`UPDATE accounts SET balance = balance - X`) теряет историю, не даёт аудита, ломается при конкурентных изменениях. Double-entry — стандарт финансового учёта: **каждая операция порождает минимум две проводки, сумма которых равна нулю**. Баланс — не хранимое поле, а **проекция** (агрегат) над журналом.

Ключевой сигнал репо: append-only журнал + производные проекции, а не CRUD-табличка.

### 3.2. Счета (минимум для демо)

- `customer:<id>` — плательщик
- `merchant:<id>` — получатель
- `acquirer_clearing` — транзитный счёт расчётов с эквайером

> **Комиссии/сплит (`fees`) исключены** — сознательное упрощение, чтобы не размывать ядро. Отмечено в README.

### 3.3. Проводки по операциям

| Операция `pay-core` | Проводки |
|---|---|
| `authorize` | **нет проводок** (холд — не движение денег), только событие |
| `capture` | debit `acquirer_clearing`, credit `merchant` (сумма захвата) |
| `refund` | debit `merchant`, credit `acquirer_clearing` (сумма возврата) |
| `cancel` | **нет проводок** (холд снят) |

### 3.4. Инварианты

- **Главный:** для каждой логической операции **сумма debit = сумма credit**. Проверяется при записи; нарушение → отказ записи, а не «починим потом».
- **Системный:** сумма балансов всех счетов = **0** в любой момент. Проверяется тестом и эндпоинтом `GET /ledger/integrity`.
- **Баланс счёта** = `SUM(credit) − SUM(debit)` по журналу. Начинаем с честного SQL-агрегата на лету; материализация — опциональное расширение (в README как «рассмотрено»).

## 4. Durable execution (Inngest)

### 4.1. Ментальная модель

Воркфлоу — обычная TS-функция, разбитая на `step.run(...)`. Каждый шаг:
- выполняется **не более одного раза** (результат мемоизируется Inngest),
- при падении процесса воркфлоу продолжается **с несделанного шага**, а не с начала,
- ретраится по политике при транзиентной ошибке.

**Defense-in-depth (важно для README и собеса):** exactly-once обеспечивают **два независимых механизма** — мемоизация шагов Inngest + идемпотентность `pay-core` через детерминированный `Idempotency-Key`. Даже если один слой подведёт, дубля не будет. Осознанная избыточность, а не паранойя.

### 4.2. Воркфлоу

**`payment.execute`** — сквозной процесс (демо-сценарий `00-overview §8`):

```
step 1: authorize      → POST /payments                 (key = hash(runId + ":authorize"))
step 2: capture        → POST /payments/:id/capture      (key = hash(runId + ":capture"))
                         ↑ эквайер может дать 503 → Inngest ретраит шаг
step 3: post-ledger    → двойная запись по capture
step 4: finalize       → пометить run завершённым
```

**`payment.refund`:**
```
step 1: refund         → POST /payments/:id/refund       (идемпотентно)
step 2: post-ledger    → двойная запись по refund
```

**`payment.cancel`:**
```
step 1: cancel         → POST /payments/:id/cancel
step 2: (проводок нет, только событие)
```

### 4.3. Политика ретраев

- Транзиентное (503, таймаут, сеть, 5xx) → экспоненциальный backoff, ограниченное число попыток.
- Терминальное (402, 422, 409, 404) → **без ретраев**, воркфлоу идёт в компенсацию/провал.
- Вход для тестирования: симулятор эквайера в `pay-core` умеет детерминированный **`fail-then-succeed`** (первый вызов 503, второй — успех). На нём и проверяем ретраи.

## 5. Саги и компенсации

### 5.1. Модель

Каждый шаг с побочным эффектом объявляет **компенсирующее действие**. Провал на шаге N → компенсации шагов N-1 … 1 в обратном порядке.

| Шаг | Компенсация |
|---|---|
| `authorize` | `cancel` (снять холд) |
| `capture` | `refund` (вернуть захваченное) |
| `post-ledger` | **обратные проводки** (reversal) |

### 5.2. Правила (ключевые инварианты)

- **Компенсации сами идемпотентны и durable** — выполняются как `step.run(...)`, опираются на идемпотентность `pay-core`. Компенсация, выполненная дважды, не создаёт двойной возврат.
- **Компенсация ledger — НЕ удаление строк.** Журнал append-only: откат = запись **обратных проводок** (reversal), а не `DELETE`. История остаётся полной и аудируемой. Это важнейший инвариант репо.
- **Падение компенсации** → воркфлоу в явное состояние `needs_review` (dead-letter). Не проглатывать молча.
- **После компенсации:** ledger сбалансирован (сумма счетов = 0), бизнес-эффект отсутствует.

### 5.3. Реализация

Тонкий слой поверх Inngest-степов: реестр шагов с их компенсациями + обёртка, раскручивающая выполненные шаги в обратном порядке при исключении. **Пишется руками (~100-150 строк)**, без внешней saga-библиотеки — ради прозрачности. Это ровно тот код, который обсуждают на собеседовании.

## 7. Хранилище (Postgres + Drizzle)

Тот же Postgres, **отдельная схема или префикс** — не смешивать с таблицами `pay-core`.

**`ledger_entries`** (append-only, **без UPDATE/DELETE**)
- `id` (uuid, pk)
- `operation_id` (uuid) — группирует проводки одной логической операции
- `account` (text) — напр. `merchant:42`
- `direction` (enum: `debit` | `credit`)
- `amount` (bigint, minor units, > 0)
- `currency` (text)
- `payment_id` (text) — ссылка на платёж в `pay-core`
- `entry_type` (text: `capture` | `refund` | `reversal`)
- `reverses_operation_id` (uuid, nullable) — для reversal
- `created_at` (timestamptz)
- Индексы: `account`, `payment_id`, `operation_id`

**`workflow_runs`** (проекция статуса; Inngest — источник правды по шагам)
- `run_id` (text, pk)
- `workflow` (text)
- `state` (text: `running` | `completed` | `compensating` | `compensated` | `failed` | `needs_review`)
- `payment_id` (text, nullable)
- `created_at`, `updated_at`

**Гарантии записи:**
- Проводки одной операции пишутся **в одной БД-транзакции**, с проверкой инварианта debit = credit. Частичная запись невозможна.
- **Идемпотентность проводок:** UNIQUE по `operation_id` (или `(operation_id, account, direction)`) — повтор шага `post-ledger` не задваивает записи.
- Коннекты/транзакции освобождаются через `using` / `Symbol.dispose`.

## 8. Обработка ошибок

| Ситуация | Ретрай? | Поведение |
|---|---|---|
| `503` / таймаут / сеть / 5xx | да | backoff-ретрай шага |
| `402` (declined) | нет | → компенсация → `failed` |
| `422` (invalid transition) | нет | → `failed`, логируем громко (баг или гонка) |
| `409` (idempotency reuse) | нет | громкая ошибка — неверная генерация ключей |
| Несбалансированная проводка | нет | отказ записи → `needs_review` |
| Падение компенсации | ограниченно | → `needs_review` (dead-letter) |

## 9. Тестирование

**Инструмент:** Vitest + локальный Postgres (docker-compose). Inngest — в dev/тестовом режиме.

**Обязательное покрытие:**
- **Exactly-once:** принудительный повтор шага → нет второго платежа, нет задвоенных проводок.
- **Возобновление после падения:** воркфлоу, прерванный на шаге 2, продолжается со шага 2.
- **Ретраи:** `fail-then-succeed` (503 → успех) → шаг ретраится и завершается.
- **Нератраиваемое:** 402 не ретраится, уходит в компенсацию.
- **Саги:** провал на шаге 3 → компенсации шагов 2 и 1 в обратном порядке; бизнес-эффект отсутствует.
- **Инвариант ledger:** после любого сценария (успех / провал / компенсация) сумма балансов = 0.
- **Reversal, а не delete:** компенсация добавляет обратные проводки; исходные строки на месте.
- **Идемпотентность компенсаций:** двойное выполнение не создаёт двойной возврат.
- *(желательно)* **Property-тест:** на случайной последовательности операций инвариант «сумма балансов = 0» держится всегда.

## 11. Критерии готовности (DoD)

- `pnpm test` зелёный; интеграционные на реальном Postgres.
- `payment.execute` проходит демо-сценарий `00-overview §8`: эквайер даёт 503 на первой попытке → durable-ретрай → успех → корректные проводки.
- Сценарий отмены: компенсация откатывает эффект, ledger сбалансирован, **исходные проводки не удалены** (только reversal).
- Инвариант «сумма балансов = 0» держится во всех сценариях; работает `GET /ledger/integrity`.
- Повтор любого шага не создаёт дублей (два рубежа: мемоизация Inngest + идемпотентность `pay-core`).
- `isRetryable` корректно разделяет 503 (ретрай) и 402/422/409 (нет); покрыто тестами.
- Падение компенсации → явное `needs_review`, не проглатывается.
- В Inngest dashboard видны шаги, ретраи, компенсации.
- README: **«Почему Inngest, а не Temporal»** (честный трейд-офф — ключевой staff-сигнал), обоснование double-entry, объяснение defense-in-depth, раздел «рассмотрено и отклонено» (saga-библиотеки, материализованные балансы, комиссии).
- Docker-образ собирается; сервис поднимается против внешних Postgres + `pay-core`.
- **Каждый файл объясним вслух построчно.**

## 12. Сознательные упрощения

- **Комиссии/сплит (`fees`)** — исключены, чтобы не размывать ядро.
- **Материализованные балансы** — не делаем, честный SQL-агрегат на лету. При росте объёма — добавляется.
- **Saga-библиотеки** — не тянем, паттерн пишется руками ради прозрачности.
- **Testcontainers → локальный Postgres** — ради скорости.

## 13. Порядок реализации

1. `ledger/entries.ts` + `ledger/accounts.ts` — модель проводок, инвариант debit=credit. **Ядро смысла.**
2. `db/schema.ts` — таблицы, UNIQUE на `operation_id`.
3. `ledger/posting.ts` — атомарная запись группы проводок с проверкой инварианта.
4. `clients/pay-core-client.ts` — клиент к `/payments/*`, детерминированный `Idempotency-Key` от `runId` + шага.
5. `saga/retry-policy.ts` — `isRetryable`: 503 → да, 402/422/409 → нет.
6. `workflows/payment-execute.ts` — happy path + ретраи (**без компенсаций пока**).
7. `saga/saga.ts` + `ledger/reversal.ts` — компенсации.
8. `http/*` — тонкий слой запуска и чтения.
9. Тесты параллельно каждому шагу.

> **Совет по темпу:** не пытайся сделать саги сразу. Сначала ledger-модель, потом воркфлоу без компенсаций (happy path + ретраи), и только затем компенсации. Каждый кусок отдельно понятен; вместе — каша.
