## Часть I. Платёжный домен (`pay-core`)

### 1. Почему идемпотентность через UNIQUE-ограничение, а не через проверку в коде?

**Короткий ответ:** потому что «проверил → вставил» — это гонка. Арбитром должна быть БД, а не приложение.

**Обоснование.** Наивная реализация:
```
SELECT * FROM idempotency_keys WHERE key = ?   → пусто
INSERT платёж + INSERT ключ
```
Два параллельных запроса с одним ключом **оба** выполнят `SELECT`, **оба** увидят пусто, **оба** вставят. Получается двойное списание. Окно гонки — миллисекунды, но при реальном трафике это происходит регулярно (ретраи клиента, двойной клик, повтор от прокси).

Правильно: **попытаться вставить и поймать нарушение UNIQUE**. Уникальное ограничение проверяется атомарно на уровне БД — два конкурирующих INSERT'а физически не могут оба пройти. Один вставится, второй получит нарушение, и это **сигнал**, что ключ уже занят: читаем существующую строку и возвращаем сохранённый снимок ответа.

```
BEGIN
  INSERT INTO idempotency_keys (key, request_hash, ...) ON CONFLICT DO NOTHING
  ├─ вставилось (rowCount = 1) → ключ наш, выполняем операцию,
  │                              пишем платёж + события + response_snapshot
  └─ не вставилось (rowCount = 0) → ключ занят, читаем строку
       ├─ request_hash совпадает → вернуть response_snapshot (тот же результат)
       └─ request_hash другой   → 409 IdempotencyKeyReuse
COMMIT
```

**Если давят:** «а если использовать `SELECT ... FOR UPDATE`?» — можно, но это блокировка строки, которой ещё нет. Пришлось бы блокировать что-то другое (advisory lock на хеш ключа), это сложнее и медленнее. UNIQUE — проще и точнее выражает намерение.

**Почему `ON CONFLICT DO NOTHING`, а не try/catch на исключении:** в Postgres нарушение ограничения **абортит текущую транзакцию** — дальше в ней ничего не сделать без savepoint. `ON CONFLICT DO NOTHING` даёт то же поведение, но без аборта: просто `rowCount = 0`. Чище.

### 2. Почему оптимистичная блокировка (`version`), а не `SELECT ... FOR UPDATE`?

**Короткий ответ:** конфликты редки, а пессимистичная блокировка держит строку и создаёт очередь.

**Обоснование.** Два подхода к конкурентной мутации агрегата:

**Пессимистичный** (`SELECT ... FOR UPDATE`): захватываем строку в начале транзакции, все остальные ждут. Гарантирует корректность, но: держит блокировку всё время транзакции (включая, если не осторожен, сетевые вызовы), создаёт очередь, риск deadlock при захвате нескольких строк.

**Оптимистичный** (`version`): читаем с версией, пишем с проверкой, что версия не изменилась.
```sql
UPDATE payments
SET state = ?, amount_captured = ?, version = version + 1
WHERE id = ? AND version = ?   -- ожидаемая версия
```
Если `rowCount = 0` — кто-то опередил между чтением и записью. Обрабатываем явно: повтор или `409 ConcurrencyConflict`.

**Почему оптимистичный здесь:** конфликты на одном платеже — редкость (обычно один клиент ведёт один платёж). Платить очередями за защиту от редкого события невыгодно. Плюс оптимистичная блокировка не держит ничего между чтением и записью — важно, потому что между ними может быть **сетевой вызов провайдера**.

**Критическая ошибка, которую ищут:** `rowCount = 0` **нельзя проигнорировать**. Если код молча идёт дальше — потеряно обновление (lost update), классический баг. Это ровно то, что проверяют.

**Если давят:** «а если конфликты станут частыми?» — тогда оптимистичная деградирует (много повторов), и стоит переходить к пессимистичной или к сериализации через очередь на ключе платежа. Выбор зависит от профиля нагрузки, и это надо мерить, а не гадать.

### 3. Почему деньги — целые числа в минорных единицах, а не float/decimal?

**Короткий ответ:** float не представляет десятичные дроби точно, а целые центы — представляет.

**Обоснование.** `0.1 + 0.2 !== 0.3` в IEEE 754. Для денег это недопустимо: ошибки накапливаются, балансы не сходятся, аудит падает. Классика.

Варианты:
- **float/double** — запрещено, см. выше.
- **decimal/numeric в БД** — точно, но в JS всё равно приезжает как строка или теряет точность при конверсии в `number`; нужна библиотека произвольной точности, лишняя зависимость.
- **целые минорные единицы** (центы) — `bigint` в Postgres, `number`/`bigint` в TS. Точно, просто, быстро. Стандарт индустрии (так делает Stripe и большинство платёжных API).

Плюс: валюта — **явное поле**, операции между разными валютами запрещены на уровне типов. Сложить USD и EUR не должно компилироваться.

**Если давят:** «а деление, проценты, комиссии?» — там появляется вопрос округления, и его надо решать явно (banker's rounding, куда падает остаток при сплите). Мы комиссии сознательно выключили, чтобы не размывать ядро, — но проблему я осознаю и знаю, где она.

### 4. Почему state machine руками (discriminated union), а не XState?

**Короткий ответ:** прозрачность. Ядро ценности репо — инварианты переходов, их нельзя прятать за фреймворком.

**Обоснование.** XState — хорошая библиотека, но здесь она:
- добавляет слой абстракции поверх того, что и есть предмет демонстрации;
- усложняет чтение кода для того, кто оценивает мою инженерию;
- не даёт выигрыша: у нас 6 состояний и десяток переходов, это 100 строк на юнионах.

На discriminated union + exhaustive switch получаем главное: **компилятор ловит незакрытые состояния**.
```ts
switch (payment.state) {
  case 'created': ...
  case 'authorized': ...
  // забыли 'captured'
  default: {
    const _exhaustive: never = payment;   // ← ошибка компиляции
    throw new Error(...)
  }
}
```
Добавил состояние — код не собирается, пока не обработал везде. Это сильнее любого рантайм-фреймворка.

**Если давят:** «а визуализация, а иерархические состояния?» — при росте сложности (вложенные состояния, параллельные регионы, таймеры) XState начинает окупаться. У нас этого нет. Решение пересматривается, если появится.

### 5. Почему гексагон (ports & adapters)?

**Короткий ответ:** домен не должен знать про БД, HTTP и провайдера. Это даёт тестируемость и явные границы.

**Обоснование.** Три выгоды, каждая проверяемая:

1. **Домен тестируется без инфраструктуры.** Инварианты (нельзя capture > authorized) проверяются мгновенными unit-тестами, без Postgres и без сети. Быстрая обратная связь.
2. **Адаптеры взаимозаменяемы.** In-memory для тестов, Postgres для прода. Симулятор провайдера вместо реального эквайера. Один и тот же use-case работает с любыми.
3. **Границы явные.** Видно, что домен, а что инфраструктура. Когда в use-case вползает `drizzle`, это сразу заметно как нарушение.

**Что было бы без гексагона:** use-case дёргает ORM напрямую → чтобы протестировать инвариант, надо поднять БД → тесты медленные → их пишут меньше → инварианты не покрыты. Это типичная деградация.

**Если давят:** «это оверинжиниринг для CRUD» — согласен, для CRUD да. Но здесь домен **богатый**: state machine, инварианты, денежная арифметика. Именно он — предмет ценности, и его изоляция окупается. Для тонкого CRUD я бы гексагон не тянул.

### 6. Почему `withTransaction` на репозитории, а не `save(payment, events, idempotencySnapshot)`?

**Короткий ответ:** репозиторий платежей не должен знать про идемпотентность. Это разные ответственности.

**Обоснование.** Требование: ключ идемпотентности и мутация платежа должны попасть в БД **атомарно** — иначе можно записать платёж и не записать ключ (тогда повтор создаст дубль) или наоборот.

Вариант «раздутый save»: `save(payment, events, idempotencySnapshot)` — работает, но смешивает ответственности. `PaymentRepository` начинает знать про идемпотентность, которая к платежу как к домену отношения не имеет. При добавлении третьей сущности в транзакцию сигнатура распухнет снова.

Вариант `withTransaction(fn)`: репозиторий даёт транзакционный контекст, внутри которого use-case дёргает **оба** порта. Каждый порт остаётся при своей ответственности, транзакционная граница — явная и расширяемая.

```
await repo.withTransaction(async (tx) => {
  await idempotency.reserve(tx, key, hash)   // INSERT ... ON CONFLICT
  await repo.save(tx, payment, events)
  await idempotency.complete(tx, key, snapshot)
})
```

**Если давят:** «это unit-of-work, зачем паттерн» — да, это он и есть. Название неважно; важно, что транзакционная граница принадлежит use-case'у (он знает, что должно быть атомарно), а не отдельному репозиторию.

### 7. Где система **не** атомарна, и почему это нормально?

**Короткий ответ:** сетевой вызов провайдера принципиально не может быть внутри БД-транзакции. Эта щель закрывается уровнем выше.

**Это самый важный вопрос в списке.** Ответ на него отличает человека, понимающего распределённые системы.

**Проблема.** Последовательность: вызвать провайдера → записать результат в БД. Между ними можно упасть:
- провайдер **списал деньги**, БД **не записала** → у нас нет платежа, а деньги ушли;
- обратный случай (записали, не вызвали) невозможен, если порядок правильный.

Засунуть HTTP-вызов в БД-транзакцию **нельзя**: транзакция не откатит чужой сайд-эффект. Это фундаментальное ограничение, а не недоработка.

**Что делаем честно:**
- Внутри `pay-core` атомарна **только БД-часть** (ключ + платёж + события). Это заявлено явно.
- Щель закрывается **durable-слоем** (`02`): при повторе шага придёт **тот же** `Idempotency-Key` (он выводится детерминированно из `runId` + имени шага). Провайдер (в реальности — по своему идемпотентному ключу) вернёт тот же результат, а мы допишем состояние. Эффект не задваивается.
- То есть: **exactly-once достигается не транзакцией, а идемпотентностью + повтором.**

**Если давят:** «а если провайдер не идемпотентен?» — тогда единственный выход — сверка (reconciliation): периодически спрашивать у провайдера состояние и чинить расхождения. Это то, что реально делают платёжные системы. У нас симулятор идемпотентен по построению, но проблему я осознаю.

## Часть II. Надёжность и ledger (`durable-ledger`)

### 8. Почему double-entry, а не колонка `balance`?

**Короткий ответ:** баланс — это не факт, а **вывод** из истории. Хранить вывод вместо фактов — потеря информации.

**Обоснование.** Наивно: `UPDATE accounts SET balance = balance - 100`.

Что теряется:
- **История.** Почему баланс такой? Неизвестно.
- **Аудит.** Невозможно доказать корректность. Для денег это дисквалифицирующе.
- **Конкурентность.** Read-modify-write на балансе — гонка.
- **Откат.** Как отменить операцию? Только вычесть — но это не отмена, это новая операция, неотличимая от исходной.

Double-entry: **каждая операция — минимум две проводки, сумма которых = 0.** Деньги не появляются и не исчезают, они **перемещаются** между счетами.

```
capture 100:  debit  acquirer_clearing  100
              credit merchant           100
              ────────────────────────────
              сумма = 0 ✓
```

Баланс счёта = `SUM(credit) − SUM(debit)` по журналу. Это **проекция**, а не хранимое поле.

**Инвариант системы:** сумма балансов **всех** счетов = 0 **всегда**. Проверяется эндпоинтом `/ledger/integrity`. Если не 0 — где-то потеряли или создали деньги из воздуха. Это единственная проверка, которая ловит целый класс багов.

**Если давят:** «а производительность? считать агрегат каждый раз?» — да, на объёме это станет проблемой. Решение — материализованная проекция (snapshot баланса на момент + дельта). Но: **сначала правильно, потом быстро.** Материализация добавляется, когда мерили и увидели проблему, а не превентивно. Журнал остаётся источником правды, материализация — кэш.

### 9. Почему компенсация — обратные проводки, а не DELETE?

**Короткий ответ:** журнал append-only. Удаление истории — не откат, а фальсификация.

**Обоснование.** Если отменить операцию удалением строк, то:
- исчезает факт, что операция **была**;
- невозможно отличить «не было» от «было и отменили»;
- аудит невозможен;
- если что-то ещё ссылалось на удалённое — битые связи.

Правильно: **reversal** — новые проводки с обратным знаком, ссылающиеся на исходную операцию (`reverses_operation_id`).

```
исходное:  debit  acquirer_clearing 100 / credit merchant 100
reversal:  debit  merchant          100 / credit acquirer_clearing 100
           ──────────────────────────────────────────────────────
           итоговый эффект на балансы = 0 ✓, история сохранена ✓
```

Так работает настоящая бухгалтерия: проводки не стирают, их сторнируют.

**Если давят:** «журнал распухнет» — да, растёт монотонно. Решается архивацией холодных периодов и снапшотами балансов, не удалением.

### 10. Почему Inngest, а не Temporal?

**Короткий ответ:** Temporal объективно мощнее, но здесь он overkill. Выбор под контекст, а не под престиж.

**Обоснование.** Оба решают одну задачу: durable execution — процесс переживает падение и продолжается с несделанного шага, шаги выполняются exactly-once.

**Temporal:** отдельный сервер/кластер + воркеры + своя БД (часто ещё поисковый индекс). Промышленный стандарт, максимальные возможности. Цена: несколько тяжёлых компонентов, заметная кривая обучения (детерминизм workflow-кода, версионирование), а для нашей цели — «одна ссылка, чтобы потыкать демку» — практически неподъёмно на дешёвом хостинге.

**Inngest:** библиотека + лёгкий dev-сервер. Функции разбиты на `step.run(...)`, каждый шаг мемоизируется. Простая ментальная модель, быстрый локальный запуск, наглядный dashboard (видно шаги, ретраи, компенсации — это работает как демо).

**Решение и почему это сильный ответ:** durable-**паттерны** (steps, компенсации, идемпотентность, классификация ретраев) присутствуют в обоих случаях. Я говорю на языке концепций, а не конкретной библиотеки. Выбрал более лёгкий инструмент, потому что контекст — демонстрационная система на бесплатном хостинге, а не платёжный процессинг Uber.

**Это и есть staff-мышление:** не «взял самый мощный инструмент», а «понял ограничения контекста, выбрал соразмерно, могу объяснить, при каких условиях выбрал бы иначе».

**При каких условиях выбрал бы Temporal:** высокая нагрузка, долгоживущие воркфлоу (дни/месяцы), потребность в сложном версионировании, наличие платформенной команды, которая тянет кластер.

*(Актуальные лимиты бесплатного тарифа Inngest — проверить перед деплоем, они меняются.)*

### 11. Почему exactly-once обеспечивается **двумя** механизмами? Это не избыточно?

**Короткий ответ:** это defense-in-depth, и оба слоя защищают от **разных** отказов.

**Обоснование.** Два независимых механизма:

1. **Мемоизация шагов Inngest** — если шаг уже выполнен, его результат берётся из истории, повторного выполнения нет.
2. **Идемпотентность `pay-core`** — если запрос с тем же `Idempotency-Key` уже обработан, возвращается снимок, нового эффекта нет.

**Почему недостаточно одного:**
- Только Inngest: если Inngest по какой-то причине повторит шаг (баг, ручной retrigger, миграция), либо если тот же платёж инициируется вне воркфлоу — защиты нет.
- Только `pay-core`: durable-возобновление после падения работает, но каждый повтор делает лишний сетевой вызов и упирается в идемпотентность постфактум. Работает, но шумно.

Вместе: Inngest **предотвращает** повтор, `pay-core` **обезвреживает** его, если он всё же случился.

**Ключевая деталь:** второй слой работает **только** если `Idempotency-Key` выводится **детерминированно** — `hash(runId + ":" + stepName)`. Если генерить случайный UUID на каждую попытку, при ретрае придёт **новый** ключ, `pay-core` посчитает это новым запросом и создаст **дубль**. Это самая коварная ошибка в такой связке.

### 12. Почему `isRetryable()` — явная функция, а не «ретраим всё, что упало»?

**Короткий ответ:** ретрай терминальной ошибки бесполезен, а иногда опасен.

**Обоснование.** Ошибки делятся на два класса:

| Класс | Примеры | Ретрай |
|---|---|---|
| **Транзиентные** | таймаут, сеть, 5xx, провайдер временно недоступен (503) | **да** — повтор может помочь |
| **Терминальные** | отказ провайдера (402), недопустимый переход (422), конфликт ключей (409), не найдено (404) | **нет** — повтор даст тот же результат |

Ретраить `402 Declined` — бессмысленно: карта не станет платёжеспособной от повтора. Это трата времени, забивание очереди и маскировка проблемы.

Хуже: ретраить `422 InvalidTransition` — **опасно**. Это признак бага или гонки; повтор скроет его вместо того, чтобы вскрыть. Такое должно **громко падать**, а не тихо ретраиться.

Поэтому в `pay-core` ошибки провайдера **разделены на уровне HTTP-кодов**: `503` (транзиентный, ретраить) и `402` (терминальный, не ретраить). Это **контракт между репозиториями**, не косметика.

**Если давят:** «а 500 от вашего же сервиса?» — ретраибельно, но с ограничением попыток и с алертом: повторяющаяся 500 — это баг, а не транзиентный сбой.

---

### 13. Что происходит, если падает сама компенсация?

**Короткий ответ:** воркфлоу уходит в явное `needs_review`. Не проглатывается.

**Обоснование.** Компенсация — тоже сайд-эффект, она тоже может упасть. Наивный код обернёт откат в try/catch и промолчит — и система останется в **неопределённом** состоянии: не завершена и не откачена, но никто об этом не знает.

Правильно: ограниченные попытки, и если не вышло — перевести run в состояние `needs_review` (dead-letter). Это честное признание: «автоматика не справилась, нужен человек». В реальных платёжных системах именно так: есть очередь на ручной разбор, и это нормальная часть дизайна, а не позор.

**Инвариант, который держим:** даже при провале компенсации ledger остаётся **сбалансированным** (сумма счетов = 0). Мы можем не знать, что делать с бизнес-эффектом, но бухгалтерия обязана сходиться.

---

## Часть III. Общие решения

### 14. Почему Hono, а не Express/Fastify/NestJS?

- **Express** — де-факто легаси. Слабая типизация, middleware-цепочки без типобезопасности. Как сигнал — «не следит за экосистемой».
- **NestJS** — тяжёлый, декораторный, навязывает DI-контейнер и свою структуру. Прячет механику за фреймворком — ровно то, чего мы избегаем: смотрящий должен видеть **мою** архитектуру, а не Nest'овскую.
- **Fastify** — хороший выбор, быстрый, типизированный. Отклонён скорее по вкусу: Hono легче и runtime-agnostic.
- **Hono** — лёгкий, отличная типизация, работает на любом рантайме. В гексагоне HTTP — **тонкий адаптер**, ему не нужен мощный фреймворк; чем меньше, тем лучше.

**Главный аргумент:** в гексагоне HTTP-слой намеренно тощий. Тащить туда тяжёлый фреймворк — противоречие архитектуре.

---

### 15. Почему Drizzle, а не Prisma?

**Короткий ответ:** для денег нужен контроль над SQL, транзакциями и блокировками.

**Обоснование.** Нам критично уметь:
- `INSERT ... ON CONFLICT DO NOTHING` (идемпотентность);
- `UPDATE ... WHERE version = ?` с проверкой `rowCount` (оптимистичная блокировка);
- явные транзакционные границы;
- при необходимости — сырой SQL (оконные функции для проекций ledger).

Prisma абстрагирует SQL сильнее, её транзакционная модель и escape-hatch'и менее удобны, генерируемый клиент прячет то, что здесь нужно видеть. Drizzle — тонкий типобезопасный слой **над** SQL: пишешь почти SQL, но с типами.

**Если давят:** «Prisma удобнее для быстрой разработки» — согласен, для продуктовой CRUD-разработки. Здесь предмет ценности — **как именно** мы работаем с БД, и это нельзя прятать.

---

### 16. Почему `postgres.js`, а не `pg`?

Легче, современнее API, лучше работает с `using`/`Symbol.dispose` (explicit resource management — TS 5.2), из коробки нормальные типы. `pg` — проверенный, но легаси-ощущение.

---

### 17. Почему outbox **не** реализован полностью?

**Короткий ответ:** его вторая половина дублировала бы Inngest. Это осознанный отказ, а не упущение.

**Обоснование.** Outbox решает проблему: нельзя атомарно «записать в БД» и «отправить событие наружу» — это две разные системы. Паттерн: событие пишется **в ту же БД, в той же транзакции**, что и агрегат; отдельный **диспетчер** потом вычитывает таблицу и рассылает.

У outbox **две половины**:
1. **Надёжная запись** — событие и агрегат коммитятся вместе. **У нас есть** (`save(payment, events)` в одной транзакции).
2. **Надёжная доставка** — диспетчер рассылает и отмечает отправленное. **Не делаем.**

Почему не делаем вторую: надёжную доставку и durable-выполнение в нашей топологии обеспечивает **Inngest** в `02`. Свой диспетчер поверх был бы **вторым механизмом на том же месте** — сложность без выигрыша.

**Когда бы добавил:** если появится потребитель событий **вне** Inngest (аналитика, вебхуки мерчанту, другой сервис). Тогда диспетчер оправдан.

**Почему это хороший ответ на собесе:** показывает, что я знаю паттерн, понимаю **обе** его половины, и осознанно не реализовал одну — с формулировкой условия, при котором реализовал бы. Это отличается и от «не знаю про outbox», и от «навалил всё, что знаю».

---

### 18. Почему нет Turborepo?

На двух пакетах кэш тасков не окупается — `pnpm -r` достаточно. Turborepo добавляется, когда пакетов станет достаточно, чтобы кэш давал выигрыш. **Инструмент под задачу, а не под резюме.**

---

### 19. Почему in-memory адаптеры — только для тестов, а Postgres обязателен?

**Короткий ответ:** без БД теряется половина ценности репо.

Именно на БД держатся:
- идемпотентность через UNIQUE (в памяти это не гонка, а иллюзия);
- оптимистичная блокировка (`version` без реальной конкуренции бессмысленна);
- транзакционные границы;
- вообще весь `02` (append-only журнал в памяти — оксюморон).

In-memory адаптер — законный инструмент **для быстрых доменных тестов** (и демонстрация выгоды гексагона). Как продакшн-хранилище — вычёркивает payments из нарратива.

---

### 20. Почему тесты на гонки должны быть **параллельными**?

Последовательный вызов дважды **ничего не доказывает** — идемпотентность на последовательных вызовах работает даже в наивной `SELECT-then-INSERT` реализации.

Доказывает только **настоящий параллелизм**:
```ts
await Promise.all([
  post('/payments', body, { 'Idempotency-Key': key }),
  post('/payments', body, { 'Idempotency-Key': key }),
])
// → в БД ровно ОДИН платёж, оба ответа идентичны
```
Если такой тест зелёный **без** UNIQUE-ограничения — значит, он не параллелит по-настоящему, и его надо чинить, а не радоваться.

То же для оптимистичной блокировки: параллельные `capture` на один платёж → инварианты не нарушены, один из запросов получил конфликт.

## Часть IV. Мета-вопросы

### 21. «Это же оверинжиниринг для демо-проекта»

Да, для CRUD-приложения — оверинжиниринг. Но:

Цель репо — **не** сделать работающую платёжку. Цель — продемонстрировать инженерное мышление в домене, где ошибка стоит денег. Сложность здесь **предмет демонстрации**, а не побочный эффект.

При этом сложность **не наращивалась бесконтрольно** — целый список вещей выброшен осознанно (см. следующий пункт). Это и есть разница между оверинжинирингом и осознанной инженерией: не «сколько всего натащил», а **можешь ли обосновать каждое включение и каждое исключение**.

---

### 22. Что выброшено осознанно (и почему это важнее того, что включено)

| Выброшено | Почему |
|---|---|
| **Outbox-диспетчер** | Дублировал бы Inngest |
| **Multi-capture** | Усложняет инварианты, ничего не добавляет к нарративу |
| **Комиссии/сплит** | Размывает ядро; вносит вопрос округления, не относящийся к теме |
| **Turborepo** | Не окупается на 2 пакетах |
| **XState** | Прячет предмет демонстрации |
| **LangGraph** (в `03`) | То же — механика агента и есть ценность |
| **Testcontainers** | Локальный Postgres проще и быстрее |
| **`metadata`** | YAGNI — нет потребителя |
| **Материализованные балансы** | Сначала правильно, потом быстро |
| **Настоящий PCI** | Цель инженерная, не комплаенс |

**Умение отрезать — более редкий и более ценный сигнал, чем умение добавить.** Senior добавляет то, что знает. Staff отрезает то, что не нужно, и может объяснить почему.

---

### 23. «Где здесь то, что вы бы сделали иначе в проде?»

Честный список — его наличие само по себе сигнал:

1. **Reconciliation с провайдером.** У нас симулятор идемпотентен по построению. В проде нужна периодическая сверка состояний и починка расхождений — потому что реальность рассинхронизируется всегда.
2. **Наблюдаемость.** OpenTelemetry, трассировка сквозь воркфлоу, алерты на `needs_review`. Сейчас — только Inngest dashboard.
3. **Материализация балансов.** Агрегат на лету не масштабируется.
4. **Версионирование воркфлоу.** Что делать с in-flight процессами при деплое новой версии — Temporal это адресует явно, у нас нет.
5. **Партиционирование ledger.** Журнал растёт монотонно.
6. **Настоящий PCI-скоуп.** Токенизация, сегментация сети, аудит — целый отдельный мир.

**Смысл этого списка:** показать, что граница между «сделано» и «не сделано» проведена **осознанно**, а не там, где кончились силы.
