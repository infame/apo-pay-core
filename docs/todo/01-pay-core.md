# 01 — ТЗ: `pay-core` (детерминированное платёжное ядро)

> **Версия 2.** Переписано под фактическую архитектуру кода: гексагон (ports & adapters), агрегат `Payment`. Имена в этом документе соответствуют коду (источник правды — код, документ следует за ним). Outbox исключён сознательно (см. §11). Фундамент созвездия, ссылается на `00-overview`. Никакого AI внутри.
>
> **Ценность репо:** понимание платёжных инвариантов — не «списать деньги», а «списать ровно один раз».

---

## 1. Область ответственности

**Что делает:**
- Жизненный цикл платежа: authorize → capture → refund / cancel.
- Идемпотентность: повтор запроса не создаёт второй эффект.
- Детерминированная state machine с явными переходами и инвариантами.
- Симуляция провайдера (эквайринга) с управляемыми сбоями (вход для durable-ретраев в `02`).
- Персистентность в Postgres с корректной конкурентной семантикой.

**Что НЕ делает (осознанные границы):**
- Нет durable execution — ретраи и саги живут в `durable-ledger` (§02). `pay-core` даёт **безопасные для повтора** операции, на которые тот опирается.
- Нет бухгалтерского ledger — двойная запись в `02`. Здесь только состояние платежа.
- Нет LLM.
- Нет настоящей PCI-обработки: карточные данные — синтетические токены.
- **Нет outbox** — обоснование в §11.

## 2. Архитектура: гексагон (ports & adapters)

Домен не знает ни про БД, ни про HTTP, ни про провайдера. Он общается с внешним миром через **порты** (интерфейсы), которые реализуют **адаптеры**.

```
        ┌─────────────── driving adapters ───────────────┐
        │   HTTP (Hono)          │   тесты / CLI          │
        └────────────┬───────────┴────────────┬───────────┘
                     ▼                        ▼
              ┌──────────────── use cases ─────────────────┐
              │  CreatePayment · CapturePayment ·           │
              │  RefundPayment · CancelPayment · GetPayment │
              └──────────────────┬─────────────────────────┘
                                 ▼
                     ┌───────────────────────┐
                     │   ДОМЕН: Payment      │  ← чистый TS, ноль зависимостей
                     │   state machine,      │
                     │   инварианты, Money   │
                     └───────────────────────┘
                                 │
        ┌────────────── driven ports (интерфейсы) ─────────┐
        │ PaymentRepository │ IdempotencyStore │ PaymentProvider │
        └────────┬──────────┴────────┬─────────┴────┬───────────┘
                 ▼                   ▼              ▼
        ┌──────────────── driven adapters ─────────────────┐
        │  Postgres/Drizzle │ Postgres/Drizzle │ Simulator  │
        │  InMemory (тесты) │ InMemory (тесты) │ Mock (тест)│
        └──────────────────────────────────────────────────┘
```

**Почему так (для README и для собеса):**
- Домен тестируется без БД и без сети — мгновенные unit-тесты на инвариантах.
- Адаптеры взаимозаменяемы: in-memory для быстрых тестов, Postgres для прода и интеграционных.
- Границы явные: видно, что домен, а что инфраструктура. Это отличает staff-код от «сервис дёргает ORM».

**Порты (driven):**

| Порт | Назначение | Адаптеры |
|------|-----------|----------|
| `PaymentRepository` | Загрузка/сохранение агрегата `Payment` + событий одной транзакцией, с конкурентной семантикой | Postgres (Drizzle), InMemory |
| `IdempotencyStore` | Резервирование ключа, сохранение/чтение снимка ответа | Postgres (Drizzle), InMemory |
| `PaymentProvider` | Обращение к внешнему PSP / симулятору эквайринга (`authorize`/`capture`/`refund`) | Simulator (детерминированный / рандомный), Mock |

**Важно:** in-memory / mock адаптеры — **только для тестов и демо**. Postgres-адаптер обязателен (§4, DoD §10). Без БД теряются идемпотентность через уникальное ограничение и конкурентность, то есть половина ценности репо.

## 3. Домен

### 3.1. Агрегат `Payment`

Центральная сущность: одна попытка провести платёж через полный жизненный цикл. Discriminated union по состоянию + exhaustive switch (без XState — прозрачность важнее). Файл: `src/domain/payment.ts`.

**Состояния:**

| Состояние | Смысл | Терминальное? |
|-----------|-------|---------------|
| `created` | Создан, ещё не отправлен провайдеру | нет |
| `authorized` | Средства захолдированы | нет |
| `captured` | Средства списаны (полностью/частично) | нет |
| `partially_refunded` | Часть захваченного возвращена, остаток можно добрать | нет |
| `refunded` | Возврат проведён полностью | да |
| `failed` | Отклонён провайдером / ошибка | да |
| `canceled` | Отменён до захвата (снятие холда или отказ до авторизации) | да |

> **Терминология:** используем `cancel`/`canceled` (как в Stripe), а не легаси-«void». Покрывает и «отказ до авторизации» (`created → canceled`), и «снятие холда» (`authorized → canceled`).

**Разрешённые переходы (как в коде):**

```
created            ──▶ authorized          (провайдер одобрил hold)
created            ──▶ failed              (провайдер отклонил)
created            ──▶ canceled            (отказ до авторизации)
authorized         ──▶ captured           (захват, полный или частичный)
authorized         ──▶ failed             (сбой на захвате, по политике)
authorized         ──▶ canceled           (снятие холда)
captured           ──▶ refunded           (полный возврат)
captured           ──▶ partially_refunded (частичный возврат)
partially_refunded ──▶ partially_refunded (добор частичного возврата)
partially_refunded ──▶ refunded           (добор до полной суммы)
```

> **Multi-capture (`captured → captured`) исключён** — усложняет инварианты, не добавляет к нарративу. Отмечено в README как сознательное упрощение. Частичный захват поддержан (единый), остаток не докапчивается.

**Инварианты переходов:**
- Из терминальных состояний (`refunded`, `failed`, `canceled`) переходов нет.
- Нельзя `capture` больше, чем `authorized`.
- Сумма всех `refund` ≤ сумма `captured`.
- Недопустимый переход → `IllegalStateTransitionError` (типизированная), не молчаливая мутация.
- Exhaustive switch: новое состояние без обработки → **ошибка компиляции** (через `never` в `default`).

### 3.2. Денежные инварианты (ядро ценности)

- **Ровно один раз:** идемпотентный ключ + уникальное ограничение БД (§4.2).
- **Целочисленные минорные единицы** (центы). Никаких float. Валюта — явное поле; операции между разными валютами бросают `CurrencyMismatchError`.
- **`capturedAmount − refundedAmount ≥ 0`** всегда.
- Частичные capture/refund: сумма частей не превышает родительскую.
- Всё покрыто тестами (§9).

## 4. Персистентность (Postgres + Drizzle)

Живёт **в адаптерах**; домен об этом не знает.

### 4.1. Таблицы

**`payments`**
- `id` (uuid, pk)
- `state` (text)
- `currency` (text)
- `amount_authorized` (bigint, minor units)
- `amount_captured` (bigint, default 0)
- `amount_refunded` (bigint, default 0)
- `provider_ref` (text, nullable до авторизации)
- `metadata` (jsonb, nullable)
- `version` (int) — оптимистичная блокировка
- `created_at`, `updated_at` (timestamptz)

**`payment_events`** (append-only история переходов)
- `id` (uuid, pk)
- `payment_id` (fk)
- `type` (text: payment.created / authorized / captured / refunded / failed / canceled)
- `payload` (jsonb — сумма, providerRef, reason и т.п.)
- `occurred_at` (timestamptz)

> Это те же события, что агрегат отдаёт через `pullEvents()`, а репозиторий пишет **в той же транзакции**, что и состояние (надёжная запись — половина outbox; см. §11).

**`idempotency_keys`**
- `key` (text)
- `operation` (text)
- `request_hash` (text)
- `payment_id` (fk, nullable)
- `response_snapshot` (jsonb)
- `created_at`
- **UNIQUE `(key, operation)`** ← БД-гарантия «ровно один раз»

### 4.2. Конкурентность (важная часть сигнала)

- Идемпотентность опирается на **уникальное ограничение БД**, а не на «проверили → вставили» (это гонка). Вставка ключа и мутация платежа — **в одной транзакции БД**.
- Мутации агрегата — под **оптимистичной блокировкой** через `version`. Конфликт → повтор или `409`. (Альтернатива: `SELECT … FOR UPDATE`; выбор фиксируется в README с обоснованием.)
- Коннекты и транзакции освобождаются через `using` / `Symbol.dispose`.

## 5. Use cases

Тонкий слой между HTTP и доменом (`src/app/*.ts`). Каждый: провалидировать вход (Zod) → проверить идемпотентность → загрузить/создать агрегат → **провалидировать доменный переход (домен бросает типизированные ошибки)** → дёрнуть `PaymentProvider` → сохранить → записать снимок идемпотентности → вернуть результат.

| Use case | Файл | Статус |
|----------|------|--------|
| `CreatePayment` (создать + authorize) | `create-payment.ts` | ✅ готов |
| `CapturePayment` (захват, полный/частичный) | `capture-payment.ts` | ✅ готов |
| `RefundPayment` (возврат, полный/частичный) | `refund-payment.ts` | ✅ готов |
| `CancelPayment` (снятие холда / отказ) | `cancel-payment.ts` | ⏳ TODO |
| `GetPayment` (состояние + история) | `get-payment.ts` | ⏳ TODO |

**Порядок операций (важное решение, объяснимо на собесе):** доменный переход валидируется **до** вызова провайдера — провайдер никогда не двигает деньги на нелегальном переходе. Персистентность — только после подтверждения провайдера; если провайдер упал, ничего не сохранено и снимок идемпотентности не записан → операция безопасно повторяется.

Use case не знает про Hono и Drizzle — только про порты. Это и делает его тестируемым на in-memory адаптерах.

## 7. Симулятор провайдера — ⏳ TODO (сейчас только Mock)

Адаптер порта `PaymentProvider`. На данный момент есть `MockProvider` (`src/adapters/mock/`), который отклоняет суммы с `amount % 100 === 13`. Целевой симулятор:

- Режим **`deterministic`** — по сиду или полю в `metadata`: approve / decline / **fail-then-succeed** / timeout. Нужен для воспроизводимых тестов и сквозного демо (`00-overview §8`: провайдер падает на первой попытке).
- Режим `random` — вероятностные сбои для exploratory-тестов.
- Различает **транзиентный** сбой (успех при повторе) и **терминальный** decline. Критично: `durable-ledger` (§02) строит на этом политику ретраев.

## 8. Обработка ошибок

Типизированные доменные ошибки с машинным `code` (`src/domain/errors.ts`, наследуют `DomainError`). Маппинг в HTTP — на границе адаптера, единообразно, без утечки стек-трейсов.

| Ошибка (в коде) | HTTP | Когда |
|-----------------|------|-------|
| `IllegalStateTransitionError` | 422 | Недопустимый переход |
| `AmountExceededError` | 422 | Capture/refund больше допустимого |
| `IdempotencyConflictError` | 409 | Тот же ключ, другое тело |
| `PaymentNotFoundError` | 404 | Нет платежа по id |
| `ProviderDeclinedError` | 402 | Провайдер отклонил (терминально) |
| `ProviderUnavailableError` ⏳ | 503 | Транзиентный сбой (ретраибельно) — появится с симулятором |
| Zod `ValidationError` | 400 | Вход не прошёл валидацию |

Разделение 402 / 503 — не косметика: это **контракт с `02`** о том, что ретраить, а что нет. `ProviderUnavailableError` вводится вместе с симулятором (§7); сейчас провайдер отклоняет только терминально.

## 9. Тестирование

Гексагон даёт двухуровневую стратегию.

**Уровень 1 — доменные unit-тесты (быстрые, без инфраструктуры):**
- Все разрешённые переходы + репрезентативные запрещённые (каждый → корректная ошибка).
- Денежные инварианты: capture ≤ authorized; сумма refund ≤ captured; частичные операции.
- Exhaustiveness: необработанное состояние не компилируется.

**Уровень 2 — use-case тесты (сейчас на in-memory адаптерах; позже — интеграционные на реальном Postgres):**
- Идемпотентность: повтор с тем же телом → тот же результат без второго эффекта; другое тело → `409`.
- **Конкурентность** (после Postgres-адаптера): параллельные мутации одного платежа не нарушают инварианты (гонка на `version`).
- **Гонка идемпотентности** (после Postgres): два одновременных запроса с одним ключом → ровно один эффект (проверка, что спасает именно UNIQUE-ограничение).
- Симулятор: approve / decline / fail-then-succeed.

**Инструмент:** Vitest. Postgres — локальный из docker-compose (проще и быстрее, чем Testcontainers; сознательное упрощение ради темпа, отмечено в README).

**Текущий статус:** `pnpm test` = 31 зелёных (money, payment-домен, create/capture/refund use-cases на in-memory).

## 10. Критерии готовности (DoD)

- `pnpm test` зелёный: доменные unit-тесты + интеграционные на реальном Postgres.
- **Postgres-адаптеры реализованы** для `PaymentRepository` и `IdempotencyStore`. In-memory остаются только для тестов.
- Все состояния/переходы реализованы; запрещённые дают типизированные ошибки. ✅ (домен)
- Все мутирующие use-cases реализованы (create/capture/refund/cancel) + `GetPayment`.
- Идемпотентность гарантирована UNIQUE-ограничением; покрыта тестом гонки.
- Денежные инварианты держатся под конкурентной нагрузкой (тест).
- Симулятор поддерживает детерминированный `fail-then-succeed` (нужен для демо и для `02`).
- Ошибки разделены на ретраибельные (503) и терминальные (402) — контракт с `02`.
- README: назначение, запуск, разбор гексагона (**зачем порты**), разбор state machine, раздел «рассмотрено и отклонено» (Express/Nest/Prisma/XState/**outbox**/multi-capture/Testcontainers).
- Docker-образ собирается; сервис поднимается против внешнего Postgres.
- **Каждый файл объясним вслух построчно** (правило `00-overview §9`).

## 11. Сознательные упрощения (и почему)

Фиксируются в README — сам факт осознанного отказа с обоснованием является staff-сигналом.

- **Outbox исключён.** Transactional outbox решает атомарность «записал в БД + излучил событие». У него две половины: надёжная **запись** и надёжная **рассылка**. Запись у нас уже есть — `PaymentRepository.save(payment, events)` пишет агрегат и события одной транзакцией. Рассылку в нашей топологии обеспечивает Inngest в `durable-ledger` (§02); свой диспетчер поверх был бы вторым механизмом на том же месте. Добавляется позже, если появится потребитель событий вне Inngest. **Осознанный отказ, не упущение.**
- **Multi-capture исключён** — усложняет инварианты, ничего не добавляет к нарративу.
- **Комиссии/сплит** — не здесь (и в `02` выключены), чтобы не размывать ядро.
- **Testcontainers → локальный Postgres** — ради скорости сборки и простоты деплоя.
- **Не настоящий PCI** — токены синтетические; цель репо инженерная, не комплаенс.
